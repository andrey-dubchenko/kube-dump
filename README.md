# kube-dump

Утилита для снятия JVM thread dump и heap dump с подов Kubernetes-сервиса. Для каждого пода она:

1. передаёт в контейнер бинарник [jattach](https://github.com/jattach/jattach) потоком через `kubectl exec -i` (в `/tmp`);
2. **thread dump:** запускает `jattach 1 jcmd "Thread.print -l"`, дамп возвращается по каналу `exec` и **не попадает в stdout контейнера**, то есть в Elastic и другие сборщики логов;
3. **heap dump:** просит JVM записать `.hprof` в `/tmp` пода (`GC.heap_dump`), потоком копирует файл на вашу машину и удаляет его в поде;
4. удаляет бинарник из контейнера и печатает сводку по состояниям потоков.

Других способов (`kill -3`, чтение логов пода) утилита не использует.

## Требования

- Go (для сборки);
- `kubectl` в `PATH` и настроенный kubeconfig (`~/.kube/config` или `$KUBECONFIG`);
- в контейнере: `sh`, `cat`, `chmod`, `rm`, доступный на запись `/tmp`, JVM как PID 1, тот же пользователь, что у JVM;
- локальный статический linux-бинарник `jattach` под архитектуру пода (скачайте сами, [релизы](https://github.com/jattach/jattach/releases)).

## Сборка и запуск

Сборка скриптом (Windows: PowerShell `make.ps1`; Linux, macOS, а также Windows с GNU make: `Makefile`; цели одинаковые):

| Цель | Что делает |
|------|-----------|
| `build` (по умолчанию) | собирает для этой машины (`kube-dump.exe` или `kube-dump`) |
| `windows` | `dist/windows-amd64/kube-dump.exe` с иконкой и версией |
| `linux` | `dist/linux-amd64/`: бинарник, `kube-dump.desktop`, иконки, `install.sh` |
| `dist` | обе сборки подряд (кросс-компиляция работает с любой ОС) |
| `check` | `gofmt` + `go vet` + тесты |
| `test`, `vet`, `fmt` | отдельные проверки |
| `icons` | перерисовывает `assets/icon.ico` и PNG-иконки |
| `resources` | пересобирает ресурсы Windows (нужен `windres` из MinGW) |
| `clean` | удаляет `dist` и собранные бинарники |

```powershell
.\make.ps1 dist          # Windows
```

```bash
make dist                # Linux / macOS
make install             # собрать для Linux и установить в ~/.local (PREFIX=/usr/local для всей системы)
```

Без скрипта достаточно `go build -o kube-dump ./cmd/kube-dump`. Версия вшивается в бинарник (`-ldflags "-X main.version=..."`, по умолчанию из `git describe`) и печатается `kube-dump -version`.

Запуск:

```bash
./kube-dump                       # параметры из configuration.yml
./kube-dump -service my-service   # один сервис, без меню
./kube-dump -module my-module     # выбор среди сервисов my-module-*
./kube-dump -env my-context       # другой контекст kubeconfig
```

Если не заданы ни `service`, ни `module`, имя модуля спрашивается интерактивно. После каждого запуска утилита возвращается к списку сервисов, пока вы не выйдете. Ctrl+C в форме возвращает к списку, а не завершает программу. Если stdin не терминал, вместо меню со стрелками показывается нумерованный список.


Конфигурация: скопируйте [configuration.example.yml](configuration.example.yml) в `configuration.yml` и поправьте под себя (`namespace`, `env`, `module`, путь к `jattach`). `configuration.yml` в `.gitignore`, в репозиторий попадает только пример.

### Иконка

- **Windows.** Иконка и сведения о версии (описание, имя продукта) вшиты в `kube-dump.exe` готовым объектным файлом [cmd/kube-dump/resource_windows_amd64.syso](cmd/kube-dump/resource_windows_amd64.syso): Go подхватывает его сам на Windows (на других ОС он игнорируется), поэтому достаточно обычной сборки, в том числе кросс-сборки с Linux.
- **Linux.** Исполняемый файл ELF не может нести иконку в себе: среды рабочего стола берут её из `.desktop`-файла и темы значков. Поэтому `make linux` кладёт в `dist/linux-amd64/` бинарник, `kube-dump.desktop` и иконки в раскладке freedesktop `hicolor` (16–256 px), а `install.sh` ставит всё вместе: `sh install.sh` в `~/.local`, `PREFIX=/usr/local sh install.sh` для всей системы, `sh install.sh uninstall` удаляет. После установки kube-dump виден в меню приложений с иконкой (запускается в терминале).

Чтобы поменять рисунок или версию: правьте [assets/genicon.go](assets/genicon.go) или [assets/kube-dump.rc](assets/kube-dump.rc), затем `make icons resources` (`.\make.ps1 icons`, `.\make.ps1 resources`).

## Флаги командной строки

| Флаг | Описание |
|------|----------|
| `-config <путь>` | Путь к файлу конфигурации (по умолчанию `configuration.yml`). |
| `-env <имя>` | Контекст kubeconfig; переопределяет `env` из конфига. |
| `-service <имя>` | Точное имя сервиса; переопределяет `service` и `module` из конфига. |
| `-module <имя>` | Модуль: выбор среди сервисов `<имя>-*`; переопределяет `service` и `module` из конфига. |
| `-mode thread\|heap\|both` | Что снимать, когда сервис задан (переопределяет `mode` из конфига). В интерактивном режиме тип выбирается в меню после выбора сервиса. |
| `-pod <имя>\|*` | Только этот под; `*` — все поды. Heap dump нескольких подов без явного `-pod` не запускается. |
| `-analyze <файл.hprof>` | Не обращаться к кластеру: разобрать уже сохранённый heap dump, вывести сводку и записать `<файл>.summary.txt`. Конфиг не нужен. |
| `-yes` | Не спрашивать подтверждение перед heap dump (переопределяет `heap_confirm`). |

Если заданы и `-service`, и `-module`, приоритет у `-service`.

## Параметры конфигурации

Файл в формате YAML. Обязательны `namespace` и `jattach`.

| Параметр | По умолчанию | Описание |
|----------|--------------|----------|
| `namespace` | — (обязателен) | Namespace, в котором ищутся сервисы и поды. |
| `service` | пусто | Точное имя сервиса. Если задано, меню не показывается: один прогон и выход. |
| `module` | пусто | Префикс модуля: предлагаются сервисы `<module>-*`. Значение с символами `*`, `?`, `[` используется как glob (например `my-*-api`). Если пусто и `service` тоже пусто, имя модуля запрашивается интерактивно. |
| `env` | пусто | Имя контекста из kubeconfig. Пусто — текущий контекст. Несуществующее имя даёт ошибку со списком доступных контекстов. |
| `jattach` | — (обязателен) | Путь к локальному бинарнику jattach (статическая linux-сборка). Относительный путь считается от рабочего каталога. |
| `container` | пусто | Имя контейнера для подов с несколькими контейнерами. Пусто — контейнер по умолчанию. |
| `output` | `dumps` | Каталог для результатов. |
| `heap_summary` | `true` | После копирования heap dump прочитать его локально и записать рядом гистограмму классов `heap_<pod>_<время>.summary.txt`. Ничего никуда не отправляется. |
| `heap_top` | `30` | Сколько строк в каждом разделе сводки (не меньше 1). |
| `kubectl_timeout` | `60s` | Предел для одного вызова kubectl (get, exec, загрузка jattach, thread dump). Зависший вызов убивается с ошибкой «timed out». |
| `heap_timeout` | `15m` | Сколько JVM может писать heap dump. |
| `copy_idle_timeout` | `60s` | Если от пода при копировании heap dump долго нет данных, копирование перезапускается с того места, где остановилось (до 5 попыток). |
| `remote_dir` | `/tmp` | Каталог внутри пода для бинарника jattach и файла heap dump. Абсолютный путь из букв, цифр и `. _ - /`; JVM должна иметь право писать туда, места должно хватать на кучу. |
| `mode` | `thread` | Что снимать, когда сервис задан (`service` или `-service`): `thread`, `heap`, `both`. В интерактивном режиме тип выбирается в меню. Переопределяется `-mode`. |
| `pod` | пусто | Только этот под (`*` — все поды). Heap dump нескольких подов без имени пода или `*` не запускается. Переопределяется `-pod`. |
| `heap_confirm` | `true` | Спрашивать подтверждение перед heap dump. `-yes` отключает вопрос на один запуск. |
| `heap_live_only` | `true` | `true` — `GC.heap_dump` только по живым объектам (перед дампом полная сборка мусора, файл меньше); `false` — `-all`, с недостижимыми объектами, больше файл, без принудительной сборки. |

## Heap dump

В интерактивном режиме после выбора сервиса (Enter) выбирается тип: **Thread dump**, **Heap dump** или **Both**. Для heap dump сервиса с несколькими подами нужно выбрать один под (или явно «все»). Heap dump снимается только для одного сервиса за раз.

Перед снятием утилита показывает занятую кучу и свободное место в `/tmp` пода, отказывается работать, если места не хватает, и просит подтверждение (`-yes` отключает вопрос). После снятия размер скопированного файла сверяется с размером в поде, файл в поде удаляется в любом случае.

Что нужно учитывать:

- **JVM останавливается** на время записи (секунды-минуты для больших куч); по умолчанию перед дампом идёт полная сборка мусора. Если у пода есть liveness-проба, Kubernetes может перезапустить его посреди дампа.
- **Размер** файла примерно равен занятой куче; `/tmp` пода должен её вместить (если это `emptyDir` или эфемерное хранилище с лимитом, переполнение выселит под).
- **Секреты и персональные данные.** В heap dump попадает всё содержимое памяти, включая пароли и токены. Храните и передавайте файл как данные из БД.
- В stdout контейнера ничего не пишется, как и для thread dump.

### Сводка по heap dump

После копирования файла kube-dump разбирает `.hprof` потоково (память не зависит от размера дампа; около 70 МБ/с на обычном диске) и пишет рядом `heap_<pod>_<время>.summary.txt`: топ классов по размеру и по числу экземпляров и самые большие массивы. Размеры считаются по данным полей и массивов, заголовки объектов в дампе отсутствуют, поэтому цифры немного занижены, а ссылки считаются по размеру идентификатора в дампе (в JVM со сжатыми указателями реальные ссылочные массивы вдвое меньше). Для ответа на вопрос «что занимает память» этого достаточно; удерживаемый размер и цепочки ссылок (поиск утечек) даёт только Eclipse MAT или VisualVM на самом файле.

Сводку можно сделать и для уже снятого дампа: `kube-dump -analyze dumps/<env>/<service>/heap_<pod>_<время>.hprof`.

## Результаты

Дампы складываются по контуру и сервису, по одному файлу на под:

```
<output>/<env>/<service>/
    thread_<pod>_<ГГГГММДД>_<ЧЧММСС>.dump
```

Например: `dumps/my-context/my-service/thread_my-service-6498857859-abcde_20260921_141915.dump`. Время в имени — момент снятия дампа (локальное), повторные запуски добавляют новые файлы в ту же папку сервиса. Каталог создаётся при первом сохранённом дампе, поэтому неудачный запуск не оставляет пустых папок.

Heap dump сохраняется рядом: `heap_<pod>_<ГГГГММДД>_<ЧЧММСС>.hprof`. Файл thread dump содержит дамп так, как его вернула JVM (`jcmd Thread.print -l`: потоки, блокировки `ownable synchronizers`, отчёт о deadlock, если он есть). В консоль для каждого пода выводится таблица «состояние потока — количество», а для сервиса с несколькими подами ещё и общий итог. Код возврата — `1`, если хотя бы один под или сервис не удалось обработать (в режиме без меню).

## Структура проекта

```
cmd/kube-dump/      точка входа: флаги и связка пакетов (+ ресурсы Windows .syso)
internal/config/    разбор и проверка configuration.yml
internal/kube/      вызовы kubectl с таймаутами, сервисы и поды
internal/collect/   снятие thread и heap dump через jattach, копирование, очистка при Ctrl+C
internal/threaddump/  разбор вывода jcmd Thread.print
internal/hprof/     потоковый разбор .hprof в гистограмму классов
internal/size/      форматирование размеров
internal/ui/        меню и подтверждения (стрелки / нумерованный список)
test/               тесты, по одному каталогу на пакет (внешние, через экспортируемый API)
assets/             иконка: генератор, .ico, PNG, .rc для Windows
packaging/linux/    .desktop и install.sh
Makefile, make.ps1  сборка
```

## Тесты

Тесты лежат отдельно от исходников, в `test/` (по каталогу на пакет), и проверяют пакеты только через их экспортируемый API:

```bash
make check          # gofmt + go vet + тесты
go test ./...       # только тесты
```
